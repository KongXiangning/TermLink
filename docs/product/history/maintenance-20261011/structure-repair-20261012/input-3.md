# TermLink 再次整理方案：从原始范围与分类备注形成可追溯产品结构

基线：`TermLink@00937429a2f7ea6166e12c0dcf97e0fa64ba558e`，分支 `codex/termlink-evidence-checkpoint`。

依赖：使用第一份方案生成并核对过的新维护指引；配合第二份方案验证页面。此次整理不改业务代码，不改 Task 历史，不引入原本未采用的产品承诺。

## 1. 本轮最终结果

将原始产品要求及后续有效变更组成的当前业务全貌，落实为：明确总目标、合适的父需求、可追踪的具体子要求、真实来源及 Task 关联；仍只是分类或正文细节的内容准确保留其性质。

现有分类并非无效，需要保留其有用映射；修复的是它没有完成核心结构交接、部分关系采用标准过窄及独立功能节点不足。

通过条件不是“所有节点都连起来”或“213 个功能全部绿色”，而是本次已采用且来源明确的层级不遗漏，已知当前范围有去向，独立细项能被消费者读取，真实未决有明确入口。

## 2. 基线事实与准备工作

基线登记了八份管理文档。此前验证记录记载 76 个可用条目、25 个需求、213 条功能描述和37行基准映射；这些是当时整理记录，不是本次已重新执行的统计或全部产品功能总数。[T2][T3]

MANAGED_REQUIREMENTS.md 为 v2，其功能点主要是条目正文内局部编号；GOALS/PROJECT 已有 v3 内容。product_classification 不是通用图契约，不能把分类计数当作独立子需求计数。[T4]

实施先确认实际工作副本、工作区修改、PRODUCT 及已安装 helper/Skill/contract。此前 maintain-project 主 Skill 与 update 指引已与 vNext 89d2ffe 源内容相同；不能把“重装同一版本”当作修复。需要安装的是第一份方案实际修订后的匹配资产，遵守既有升级/漂移保护，保留项目自定义配置和业务边界。

不强制 reset、rebuild 旧记录或全量迁移历史；独立验证环境与真实业务工作副本分别标明。

## 4. 总目标和上层结构

### 4.1 保留已有总目标身份

复用 `GOAL-TERMLINK`。已有维护决定记载采用的总目标为“移动优先的远程终端系统，让浏览器与 Android 稳定访问终端，并支持 Codex 同一会话连续体验”。整理时核对该来源及后来有效修订，不从零发明根目标，也不因本轮分类改变就生成新的目标版本。[T5]

当前规范里“所有目标/关系只属 Agent 推断”等过宽表述，应按实际证据逐项纠正：已采用根目标保持采用依据，确实仍为推断的旧子目标关系继续保留其真实性。历史用户纠正和维护记录不改写；本轮纠正的是当前解释及落地结果。

### 4.2 默认采用的阅读层级

按用户已明确的管理思路，以以下层级组织；该图是整理框架，不是穷尽业务清单，也不自动恢复已退出模式：

```text
GOAL-TERMLINK
├─ 服务端能力要求
│  ├─ 认证、权限与审计
│  ├─ 终端/会话能力
│  ├─ Codex 接入（具体模式依据当前采用范围）
│  ├─ 安装与发行中属于服务端的既有范围
│  └─ 历史采集与持久化的既有范围
├─ Web 客户端能力要求
│  └─ 实际采用的终端、会话及其他能力
└─ App 客户端能力要求
   ├─ 终端模式
   └─ Codex 模式
```

每个有业务边界和核对意义的高层能力使用父 requirement。上层以 supports 指向实际目标，下层以 part_of 指向父 requirement；具体功能继续分解。共享的会话、历史、证书或其他能力用同一身份在适用路径引用，不复制成几个端侧同名要求。

“服务端/Web/App”是用户已采用的组织思路，不能仅为术语偏好强制换成 module。纯导航分组确无独立义务时才用 module 或标签。安装、跨端或维护范围如何归属，取决于实际材料，不将示意图当成强制单父树。

两个现有子目标指向根目标的关系逐项核对。充分依据支持的按实际采用记录；其他保留候选。建立已有明确父需求到根目标的合法路径，不必等待所有旧目标关系都解决，也不批量将 26 条推断关系转正。

### 4.3 不复活被排除的内容

现有用户纠正明确反对把 App 真实提权/降权回滚等未采用内容列为需求或完成障碍，本轮继续尊重。[T6] 旧 WebView 回退、传统模式或其他历史方案只有仍处于有效采用范围才显示为当前要求；不能因为用户用其举过分类例子就复活已退出义务。

Codex IPC、历史采集等既有项目技术边界继续有效。本轮不修改这些业务实现或架构要求，也不为让父级“完整”新增全设备、性能或安全认证承诺。

## 5. 25 项需求与 213 条描述的归类办法

### 5.1 一次核对所有已知去向，不机械对象化

对本次读取到的既有需求与每条功能描述，确定下列去向。若实际工作区数量变化，以真实材料为准，不为了保持基线数字截断新增范围。

| 去向 | 处理 |
| --- | --- |
| 已有合适独立 requirement | 复用该身份与正文，补采用的组成/支撑关系。 |
| 需要独立追踪的明确功能或质量要求 | 形成子 requirement，保留原编号/章节到新身份的来源映射。 |
| 一般细节、例子、验收条件 | 留在所属正文，不制造无意义对象。 |
| 跨端共用或同义重复 | 核对后共用一个真实身份；保留各来源与适用范围，不能只凭同名合并。 |
| 未采用、退出或真实未知 | 按原来源保留候选/历史/未决；不强制补正式边，不当成已满足。 |

这份去向记录是本轮迁移/整理依据，可放在现有映射章节或一份简短交接记录中；不是再建一套永久并行维护的功能库。结构完成后核心 links 为正式关系来源，旧 product_classification 和局部编号作为来源说明或历史导航，不再维护两套相互竞争的当前层级。

### 5.2 独立细项的最低内容

每个真正独立的子 requirement 使用稳定 ID、需求内容、范围边界、验收要求、原来源及 part_of。不假造 Task ID、测试结果或定义摘要。已有功能名足够具体则直接复用，不能为统一层数再创建同名下一级。

父项保留完整总体范围、共性约束和组合验收。移到子项的详细定义在父正文中改为明确引用，不能既复制一份完整细项又把两处都当作当前权威。历史原文以原文件/固定版本或必要的受影响片段保留。

历史 Task 的关联覆盖原实施范围。只有证据充分时才补到独立细项；否则保留父级关联，不把它自动发放给所有子项。

### 5.3 原始范围的遗漏核对

不能只对 25/213 个现有条目内部自洽。核对原始 P0.3、P1.11、P2.1—3 等映射中已注明不足的部分，分别说明它们是已采用但未充分定义、未来候选、已被后来具体要求覆盖，还是仍需原始材料确认。[T1]

对已经明确采用、只是尚无 Task 的义务，仍需纳入适当当前范围；概括主题中真正未确定的行为继续保留问题，不据分类自行发明具体功能。不得把“缺 Task”解释为“不能保留需求”，也不得把“原文提到”解释为其全部潜在扩展都已采用。

## 6. 版本迁移与文件写入

### 6.1 优先路径

按第一份方案，核对并通过正式 helper 将本次需要出站 requirement→requirement 关系的 `MANAGED_REQUIREMENTS.md` 迁为 v3；保留原25项的身份、实际范围、有效约束、来源和任务关联，不做业务重写。项目 manifest 继续 v2。

新增的父项/子项可以放在同一规范文件，也可以放在少量新的 v3 文件并登记 managed_paths。文件数量按可维护性选择，不按“一功能一文件”机械生成。默认不迁移全部旧 report/历史源文件。

仅把新父项放入 v3 文件，不能使旧 v2 owner 自动获得 v3 的出站 part_of 方向；实际关系所在定义文件的版本也必须适用。写入由现有 check/apply 验证，不绕过闭合契约塞入扩展字段。

### 6.2 分批保存与重试

先读实际文件摘要，使用现有局部更新/迁移能力。需要保存受影响旧内容时优先引用可恢复原版本或必要片段，不重复复制全仓库。文件处理过程中出现局部失败，保留已保存身份，补失败关系或顺序即可。

新增文件登记和身份去向必须合法；不在两个托管文件中同时保留同 ID 的当前定义。跨文件移动有必要才做，默认迁移原文件可减少身份迁移风险。

### 6.3 项目顺序

原 requirement_order 的已有相对顺序保留。新增父项及具体细项以本次采用顺序追加；图中父项置上、子项展开是展示，不要求在全局数组按树形前序重排。已登记的旧需求、历史位置和任务先后不自动改动。

### 6.4 当前结果不伪造

迁移与采用关系可能使旧报告需要定义/算法适用性核对。保留报告的原对象、时间、摘要及已交付内容；不能改旧 hash、把所有 PASS 复制到子项或因为结构整理将结果清零。

依据已有材料足够时，在授权内局部生成新的适用报告，使用实际范围与对象；不足时保留待核对。当前关系与结果选择是两项交付，结构可以先可用，不要求为绿色节点新建测试或业务验收 Task。新结构范围声明不自动等于支持关系，更不从旧报告反推新范围。

## 8. 不再整理第二次的验证

### 8.1 真实静态交接

对实际保存后的同一副本运行既有产品读取/check；记录可读条目、正式层级路径、未决关系、独立细项、正文保留项和实际未读范围。关心 adopted 的关系是否生效，不以总边数或所有孤立消失判断成功。

将这组资料交给 TraceLens：从根目标到采用的父需求，再进入至少一条较深的具体功能路径；查看共享要求、候选理由、未连入项及 Task/Step 返回。无功能报告时允许未知，但必须是对的对象和原因。

### 8.2 隔离增量演练

从整理后状态制作有限隔离工作副本，使用真实已安装的新 Skill 处理一条明确标为合成、具有确定父项的新增要求。验证一次维护后定义、关系、来源和新增顺序均可消费；重试不生成重复；真实 Task 操作不因关联失败而重做。

没有真实新增业务授权时，合成内容不写回 TermLink 业务文档，不提交成真实需求，不声称产品功能已实现。也可以使用用户后来真实采用的新需求完成这项验证，但不得为了测试而替用户采用新业务。

## 9. 验收清单

| 项目 | 通过标准 |
| --- | --- |
| 根目标 | 已有采用身份与来源保留，不从近期 Task 重新定义项目。 |
| 已采用层级 | 本次有依据的父需求/子项通过核心 links 可读；仍为候选的关系有实质说明。 |
| 功能描述去向 | 本次所选全部已知条目有去向记录，独立节点和正文细节可区分；不自称穷尽未来所有功能。 |
| 原始完整范围 | 初始范围与后续有效决定有对应和真实未决；不以 25/213 的内部计数代替完整盘点。 |
| 共享与版本 | 单一当前身份/正文，关系方向与所属文件版本适用；有必要的局部迁移不牵连全部旧资料。 |
| 顺序 | 已有相对顺序不变，新身份批次追加；分类位置不写回重排。 |
| 结果 | 不新增业务完成承诺、不把旧 PASS 分摊、不为整理重跑全部业务验证；旧成果及适用性分别保留。 |
| Task | 历史与现有 Task/Step 不因整理被重建、重开或重分配；空关联合法。 |
| 页面 | 正式路径可见，候选/未连入可解释，实际独立功能可展开，来源和 Task 导航可返回。 |
| 后续新增 | 隔离或真实采用增量在同次维护中形成结构，不再次依靠另一个手工整理请求。 |

完成说明区分结构整理、来源/范围待明确、报告待核对及 UI 配套四部分。有已采用结构未落实时不能称整体整理完成；允许合理未知留下，不强迫将其转成新产品承诺。

## 10. 最终交付物及执行边界

交付真实文档差异、必要的原到新去向记录、实际 helper 回读、有限页面操作证据、隔离增量结果及剩余事项。引用已有材料，避免每个节点单独保存大日志或证据副本。

本方案实施不包括业务修复、性能优化、全平台验收、发布部署、全历史重新审查或自动创建全部后续 Task。Git 提交、推送及真实项目升级按届时明确授权执行，不从“整理方案”自动扩大外部动作。
