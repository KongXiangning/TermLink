一、三份方案共同采用的最终口径
本轮不是让所有节点都连起来，而是让用户已经采用、且有依据的业务结构，真正保存为消费者能够识别的结构。
具体有四个关键决定。
1. 不强制引入 module 层
你希望判断“服务端要求”“权限管理要求”“某个连接模式要求”是否满足，这些有实际业务范围的内容，默认使用父需求与子需求。
纯粹用于分类导航、不单独承担交付要求的分组，才使用 module。平台标签、原文编号等可以继续作为补充信息。
现有 v3 已支持 requirement→requirement 的组成关系，能够承载这条路径，不需要新增 Feature 类型或另一套协议。
2. 正式结构进入核心关系，不再只写分类字段
需要进入需求主图的已采用结构，必须通过稳定条目和 links 表达。
extensions.product_classification、正文目录和编号映射可以保留，但不能代替正式层级，也不能凭这些字段存在就宣称结构交接完成。
3. 功能描述与独立功能节点分开处理
TermLink 的 213 条功能描述，不应机械转换成 213 个新对象；但需要独立展开、关联 Task 或核对成果的具体要求，应使用子 requirement。
其余解释、例子和验收条件仍留在正文。不能把“功能描述已经列出”与“独立功能点管理已经实现”混为一谈。
4. Task 继续独立推进
关系未明确、功能未细化、报告未知或维护保存失败，都不单独阻塞 Task。
“同次维护”指同一授权工作过程内处理相关内容，不意味着所有文件必须一起成功，更不是新增跨文件事务或 Task 门禁。
二、方案一：vNext 结构持续维护修复
1. 修复目标
让以下链路成为正常维护行为：
新增或修改需求 → 保存完整定义 → 同步维护有依据的结构与顺序 → 回读实际结果。

不能继续形成：
写完需求正文 → 只补分类备注 → 用户发现图不对 → 再单独整理一次。

现有 update.md 已经要求完整增量分析、保留父项、维护顺序和保存采用决定。因此，本轮不是重建流程，而是补齐结构如何正式落地，以及怎样核对本次结构交付确实完成。
2. 明确 declared 的判断依据
最终规则是：
declared 取决于关系是否有明确的业务依据、是否属于已采用结构及当前授权，不取决于用户是否亲自填写内部 ID。

情况	应有行为
用户已经采用某个层级	在授权内保存明确关系，不逐边重复确认
正式源材料已明确表达组成关系	忠实结构化保存，并保留来源
明确授权整理既有范围，归属充分明确且不改变业务要求	可以保存相应结构，说明归类依据
只是盘点，模型新提出多种可能归属	保留候选或未决
来源冲突、业务边界确实不清	保留真实问题，不强行补边
旧关系曾被明确否定	尊重旧处置，不能因重试重新出现


同时禁止两个极端：
不能批量把全部 inferred 改成 declared。
也不能因为关系由 Agent 整理，就永久只能标为 inferred。
另一个需要明确的语义是：组织已有要求，不等于新增业务义务。 将已采用的服务端范围建立为父需求，把权限要求归入其中，可以只是结构化整理；但如果顺带增加全设备覆盖、安全认证或性能指标，则属于业务范围变化，不能借整理自动采用。
3. 在同一次维护中处理哪些内容
维护动作	同次应处理的内容
新增需求或独立功能点	定义、来源、适用范围、明确的归属关系及新身份的展示顺序
细化已有需求	保留父项，建立子项与组成关系，避免复制两份当前定义
修改需求范围	核对并调整实际受影响的关系与范围
采用层级或分类方案	将采用的结构落实为核心条目和关系，而不只是标签
真实替代、合并或退出	保留身份去向和来源，调整受影响关系，不继承旧 PASS
暂时无法归属	保存需求与未决信息，允许继续实施


当前交付范围内已经采用、只是排在后面实施的功能，仍然属于当前范围。不能因为暂时没有 Task，就把它降为候选或从全景中省略。
4. 回读不能只检查“文件合法”
本次修复需要增加一个明确的结果核对：
本次已采用的结构，能否通过现有核心关系被读取出来？

回读应分别说明：
哪些正式路径已经形成，哪些关系仍是候选，哪些部分未保存，哪些功能仍然只是正文细节。
不能只凭 schema valid、分类数量或文件保存成功就结束。
这项核对可以复用本次拟保存的关系和现有 product_view.current_relations，不需要建立永久“期望关系数据库”。没有父项本身不算错误；有依据、已经采用且本次应保存的关系被遗漏，才是维护未完成。
5. 具体修改位置
位置	修改内容
docs/product/project-maintenance/document-contract.md	补充关系采用、核心结构落地、同次维护及功能细项表达边界
references/update.md	承载新增、细化、修改、归类和回读的主要方法
references/inventory.md	存量整理区分父需求、纯分类和正文细节，保留原始完整范围
references/discussion.md	明确采用后衔接现有更新过程，不把讨论相关性确认当成需求采用
maintain-project 主模板	只增加必要的简短指引
使用指南、样例和生成资产	同步实际用法及安装内容


prepare-task、close-task、plan.md、reconcile.md 只核对是否正确复用这条路径；已经覆盖的部分不重复改写。
默认不修改 Schema、Task reducer、全图摘要算法、记录存储或完成判定。
6. 验收与交付
验收必须包含实际宿主操作，尤其是：
用户采用层级但没有说内部 ID；禁止新增业务但允许整理已有结构；已有父项下连续新增需求；只有盘点授权时保留推断；写冲突后只补失败部分。
格式测试和宿主行为证据分别报告。最后通过现有生成流程交付契约、references 和 Skill，核对隔离安装后的实际资产。
这里不能只重新安装当前同样的文件。上一轮已核对的两个关键安装文件与源内容一致，本次需要交付的是真正修订后的资产。
三、方案二：TraceLens 结构解释与分层展示修复
1. 保留正式关系筛选，不通过放宽解析来补线
TraceLens 当前按已定位、declared + active 的核心关系形成正式结构，这个方向保持不变。
不让 TraceLens 将 product_classification 自动转换为 module、父需求或正式连线。
它已经有候选关系的局部虚线图和来源详情，也已有需求组成及 Task 汇集能力，本轮优先复用。 
2. 主图增加“为什么没有连入”的解释
主图附近增加简短提示，例如：
当前有若干需求未通过已声明关系连入所选目标；另有候选结构关系可查看。

数量必须来自实际快照，不能硬编码 TermLink 的关系数量。读取不完整时，应说明只针对本次已读取范围。
设置两个明确入口：
入口	内容
查看候选关系	查看已记录推断的理由、来源和局部虚线关系，复用现有组件
查看未连入需求	查阅未进入当前目标图的要求，并解释其具体原因


原因至少区分：
属于其他目标、存在候选路径、核心关系尚未记录或确定、引用或身份异常。
不能统一称为“文档没有整理好”，更不能把“没有正式路径”解释成“没有实现”。
本轮不建设全项目候选叠加图。 先用已有局部关系图加直接入口解决可解释性，避免再扩一套布局和推理系统。
3. 接通实际使用页面的分层阅读
使用已有 requirementHierarchy 处理高层需求和独立子需求的展开，而不是又写一套层级算法。
默认先看高层，按需展开细项；搜索和缺口筛选保留必要祖先。共享节点保持一个身份，某条父路径收起后，只要另一条展开路径仍然有效，就不能让共享节点消失。现有辅助代码已经考虑了这类场景。
正文中的功能编号继续在正文中读取，不能自动成为独立节点和状态。
4. 修正与本轮直接相关的节点语义
当前主图对非 goal 节点统一显示“需求”，并统一进行评估选择。正式增加层级后，需要同步处理这些显示差异。
节点	最终处理
goal	显示目标；目标级结果使用该目标自身范围，与详情一致
requirement	按实际目标、范围和对象显示需求结论
module	显示模块或分类，不把它送入需求评估而显示“冲突／尚未满足”
候选关系	只表达已记录的推断，不参与正式归属和满足推导


这是保持节点语义准确，不是增加新的目标评估算法。
5. Task 与导航保持原有边界
父需求可以汇集自身与正式组成后代的 Task，保留每条关联的角色、覆盖及来源。
候选关系不能扩大正式汇集；只关联父项的 Task 不能自动分配给所有子项。真实 Task 状态与关联来源问题分开显示。
需求、来源、候选关系与 Task／Step 之间切换后，应保留目标范围、筛选、展开和必要滚动位置。
现有 Runtime 只读查询和快照降级继续使用，不新增业务写回或自动维护操作。
6. 修改位置与验收
主要修改：
文件	本轮作用
src/shared/product-view.ts 或相邻展示辅助	派生结构说明和未连入信息，保留正式选择规则
src/shared/product-hierarchy.ts	复用现有组成与 Task 汇集
src/web/product-v3.tsx	主图提示、候选及未连入入口、分层使用和节点语义
src/web/product-graph.tsx、product.tsx	复用关系、来源和详情组件
相关测试与样式	有限行为回归，不重做全站页面


验收使用三组输入：
TermLink 整理前真实资料、整理后实际保存资料、隔离副本中的后续新增场景。
这能同时证明：缺结构时解释正确，有结构时消费正确，下一次新增不需要前端为特殊字段临时写解析。
四、方案三：TermLink 目标、需求、功能再次整理
1. 本轮不是推倒重来
保留原有需求、功能描述、来源和成果。现有分类有价值，但需要将其中已经采用且应进入主图的结构落实到核心表达。
保存的维护依据明确区分了用户“按层级整理”的指令与实施者“只作为分类导航”的解释。本轮修正后者在当前文档中的不当收窄，不修改历史用户原话。
2. 以原始范围和后续有效决定为依据
读取范围以以下材料为主：
材料	用途
PRODUCT_REQUIREMENTS.md	产品定位、原始有效范围和需求分层
PROJECT.md、GOALS.md	当前总目标、范围、顺序和关系
MANAGED_REQUIREMENTS.md	原有需求身份、功能描述和分类
相关原需求、决定与变更	判断后来增加、修改、退出的真实范围
用户纠正及维护依据	保留真实约束，区分采用内容与实施者解释
现有交付报告和必要 Task 来源	核对实际成果，不反向制造需求


不能只围绕现有 25 项需求和 213 条描述做内部自洽。 原始范围中已经注明映射不足的部分，也要交代其当前去向、已退出依据或未决内容。
另一方面，不要求为本次整理重读全部大型日志或重跑全部业务测试。需要的来源未取得，明确保留，不凭局部代码补造用户承诺。
3. 保留总目标，落实采用的父需求结构
复用已有 GOAL-TERMLINK，对照已记录的总目标采用及后续有效决定，不根据近期 Task 重新总结项目目标。
按你已经明确的思路，以服务端、Web、App 作为主要阅读层次；有业务范围和达成判断意义的部分采用父 requirement：
TermLink 总目标
├─ 服务端能力要求
│  ├─ 认证、权限与审计
│  ├─ 终端与会话能力
│  ├─ Codex 接入及当前有效模式
│  ├─ 安装与发行中的相关范围
│  └─ 历史采集与持久化
├─ Web 客户端能力要求
└─ App 客户端能力要求
   ├─ 终端模式
   └─ Codex 模式

这是一份整理框架，不是完整功能清单。具体归属以真实材料为准，跨端能力保留共享身份。
原有两个子目标与总目标的关系分别核对。依据充分的正式保存，其余继续保留候选。无需等待所有旧关系确定，才能落实其他已经明确的父需求结构。
4. 对每条既有功能描述确定去向
类型	处理
已经有合适的独立 requirement	复用身份，补正确关系
应独立展开、追踪或核对的明确要求	形成子 requirement
一般细节、例子、验收条件	保留在正文
跨端共享或确实重复	核对后引用同一身份，保留各来源与适用范围
候选、退出或未知	保持真实状态与来源，不强行变为当前义务


应保留“原需求／原功能编号 → 当前去向”的整理依据，但它只是本轮迁移和核对记录，不再成为第二套需要长期同步的功能库。
把具体定义移到子项后，父项保留总体能力、共同边界和组合要求，以引用连接细节，避免两份当前正文重复。
5. 处理 v2 到 v3 的实际衔接
TermLink 当前规范需求文件还是 v2。需要新增 requirement→requirement 的出站组成关系时，应通过现有 helper 合法迁移相关定义文件，或形成版本合法的混合文档布局。
仅把新父项放在 v3 文件中，不会自动让旧 v2 条目获得 v3 的关系能力。
优先迁移实际涉及的 MANAGED_REQUIREMENTS.md，保留原身份、有效范围、来源和 TaskBinding；必要的新父项、细项放在少量规范文件内。Manifest 继续 v2，不强制迁移全部历史报告。现有契约已经提供这类 v3 表达及旧文档兼容边界。
6. 严格保持历史成果、Task 和顺序
已有 requirement_order 相对位置不变，新父项或子项按本批顺序追加。图中父项在上、子项在下，是展示组织，不是全局数组重排。
旧 Task 不因细化而重建、重开或修改原计划。关联能精确到功能点就局部补充，证据不足就继续保留父级关联。
版本或关系变化可能使报告需要适用性核对。应保留原对象、时间、摘要和成果，不能修改旧摘要来消除提示，也不能把父项旧 PASS 复制到全部子项。
此前用户已排除的 App 真实提权、降权回滚等要求，不能因“补齐父级能力”重新出现。历史模式或方案也只有仍然有效时才列为当前范围。
7. 核心验收：下一次新增无需再整理一遍
整理后，完成一次真实读回和页面核对：
从根目标到父需求，再到选定独立功能点；查看共享要求、候选理由、未连入内容和实际 Task／Step。
随后从整理后状态制作有限隔离副本，使用新安装的 Skill 处理一条有明确归属的合成增量，验证一次维护后定义、关系、顺序和来源均可消费。
合成内容只用于隔离验证，不写回 TermLink 成为真实业务要求。不能为证明系统好用，替用户采用一条新的产品功能。
五、实施次序与最终完成标准
推荐次序
阶段	工作
第一阶段	收敛 vNext 的最小结构维护规则；同时用 TermLink 真实材料复现问题
第二阶段	修订 vNext 指引和安装资产；TraceLens 并行补解释入口、分层使用及节点语义
第三阶段	使用匹配的新资产，在 TermLink 完成正式存量整理
第四阶段	用同一组资料验证生产、读取、页面及下一次增量


不需要等所有契约文字修改结束才验证，也不能只用预先手写好的完美关系文件证明修复成功。
最终完成标准
责任方	需要证明什么
vNext	有依据、已采用的结构在同次维护中形成；新增和变更不会再次退化成只写分类
TraceLens	正式结构准确显示；候选和未连入原因可解释；功能与 Task 下钻正常
TermLink	原始范围与有效增量有当前去向；采用层级进入核心结构；独立功能与正文细节可区分
联合交付	下一次有明确归属的增量无需另起一次“整理需求图”，且没有改变既有 Task、历史成果和稳定顺序


验收不要求所有关系正式化，也不要求所有节点都有满足结论。要求的是：已采用内容不能遗漏，未确定内容不能冒充已确定，格式通过不能冒充管理结果正确。
